# libquantum (SPEC CINT2006 462) — 三组对比报告

## 一、测试说明

### 1.1 测试目的

将 IPC 差异拆解为两个因素：
1. **流水线参数变化**（宽度、资源数量）—— 参数层面的影响
2. **IEW 代码修改**（多 IQ、EX1/EX2 分离、Stall 分类等）—— 代码层面的影响

### 1.2 三组配置

| 组别 | 代码 | 参数 | 说明 |
|------|------|------|------|
| A. 原始 O3 | 原始 gem5 | 原始默认（fetch=8, decode=8, rename=8, dispatch=8, commit=8） | 对照组 |
| B. 原始代码 + C910 参数 | 原始 gem5 | C910 宽度（fetch=3, decode=3, rename=4, dispatch=4, commit=3） | 仅参数变化 |
| C. C910 IEW 修改后 | 修改 gem5 | C910 宽度（同 B） | 参数 + 代码变化 |

**相同条件**：同一二进制 (libquantum shor 15)、同一 gem5 版本、同一缓存配置、同一分支预测器。

## 二、核心结果

### 2.1 IPC 对比

| 指标 | A. 原始 O3 | B. 原始+C910 参数 | C. C910 IEW 修改后 |
|------|-----------|------------------|-------------------|
| 提交指令数 | 7,860,781 | 7,860,781 | 7,860,781 |
| 执行指令数 | 8,041,691 | 7,960,689 | 7,959,779 |
| 总周期 | 4,082,861 | 5,084,632 | 5,112,592 |
| **IPC** | **1.9253** | **1.5460** | **1.5375** |
| CPI | 0.5194 | 0.6468 | 0.6504 |
| 仿真 tick | 4.08B | 5.08B | 5.11B |

### 2.2 IPC 差异归因

| 差异来源 | IPC 变化 | 相对变化 | 占比 |
|---------|---------|---------|------|
| A→B：参数变化 | 1.9253 → 1.5460 | **-19.7%** | ~97% |
| B→C：代码变化 | 1.5460 → 1.5375 | **-0.55%** | ~3% |
| A→C：总体 | 1.9253 → 1.5375 | **-20.1%** | 100% |

**关键结论：IPC 下降的 97% 来自流水线宽度参数变化（fetch=8→3 等），仅 0.55% 来自 IEW 代码修改。**

### 2.3 性能差异详解

#### A→B：参数变化的影响（-19.7%）

| 参数变化 | 原始值 | C910 值 | 影响 |
|---------|--------|---------|------|
| fetchWidth | 8 | 3 | 前端取指带宽降低 62.5% |
| decodeWidth | 8 | 3 | 译码带宽降低 62.5% |
| renameWidth | 8 | 4 | 重命名带宽降低 50% |
| dispatchWidth | 8 | 4 | 派发带宽降低 50% |
| commitWidth | 8 | 3 | 提交上限从 8 降到 3 |
| LQEntries | 32 | 16 | Load 队列减半，内存并行度降低 |
| SQEntries | 32 | 12 | Store 队列减少 62.5% |
| numPhysIntRegs | 128 | 95 | 物理寄存器减少，rename 压力增加 |
| numPhysFloatRegs | 128 | 48 | 浮点寄存器大幅减少 |

#### B→C：代码变化的影响（-0.55%）

| 代码差异 | 说明 |
|---------|------|
| 单 IQ → 8 种 typed IQ | 指令路由到特定 IQ，可能增加队列碎片 |
| IQ 溢出回退 | BIQ→AIQ0、AIQ1→AIQ0 等回退路径 |
| EX1/EX2 路径分离 | 多周期操作需要时钟边沿 WB |
| Stall 类型检测 | 额外的 stall 分类逻辑 |
| Scoreboard 增强 | 多 PRF 依赖追踪 |

0.55% 的微小说明代码修改没有引入明显的性能退化。

### 2.4 缓存性能

| 指标 | A. 原始 O3 | B. 原始+C910 参数 | C. C910 IEW 修改后 |
|------|-----------|------------------|-------------------|
| D-Cache hits | 1,919,593 | 1,930,891 | 1,934,419 |
| D-Cache misses | 9,314 | 9,236 | 9,152 |
| 命中率 | 99.52% | 99.52% | 99.53% |

三组命中率几乎一致，内存访问模式相同。

### 2.5 算法正确性

三组均正确输出：
```

```

## 四、结论

### 4.1 IEW 修改正确性

| 方面 | 结论 |
|------|------|
| 功能正确性 | 三组算法输出一致，指令数完全相同 |
| 代码退化 | IEW 代码修改仅带来 0.55% 的微小说明性能影响 |
| 主要差异来源 | 97% 的 IPC 差异来自流水线宽度参数，完全可预期 |
| 缓存一致性 | 三组命中率均为 ~99.53%，内存行为一致 |
| 统计增强 | 修改后提供了 Pipe 计数、Stall 分类、EX1/EX2 等可见性 |

### 4.2 IPC 差异总结

```
原始 O3 IPC 1.9253
    │
    ├─ 流水线宽度收窄 (fetch 8→3, commit 8→3, etc.)
    │  └→ IPC 1.5460  (-19.7%, 占总差异的 97%)
    │
    └─ IEW 代码修改 (8 typed IQs, EX1/EX2, etc.)
       └→ IPC 1.5375  (-0.55%, 占总差异的 3%)
```

### 4.3 设计合理性

- **C910-like IPC = 1.54** 在 3-width commit 限制下是合理的
- **参数变化主导性能**：这是预期的，因为 fetchWidth=3 直接限制了进入流水线的数据量
- **代码修改性能中性**：0.55% 的额外开销在测量误差范围内，说明 typed IQ 路由、EX1/EX2 分离等机制没有引入显著的性能惩罚
- **统计价值**：修改后的 IEW 提供了原始 gem5 无法提供的流水线细节（8 Pipe 分布、10 种 Stall 类型、EX1/EX2 分离等），对验证 OpenC910 IEW 正确性至关重要
